## Deviations from the original plan

- **`sfdp` dropped from the Graphviz engine list** — Alpine's graphviz package isn't compiled with GTS triangulation support, so sfdp errors out. The other five engines (`dot`/`neato`/`fdp`/`circo`/`twopi`) cover every layout we need.
- **JRE swap: `openjdk17-jre-headless` → `openjdk17-jre`** — headless variant lacks `libfontmanager.so`, which PlantUML and ditaa both require for SVG/PNG text rendering. Cost: ~+4 MB image size.
- **jp2a build deps grew** — Talinx fork pulled in `libpng-dev`, `libwebp-dev`, `libexif-dev` on top of `libjpeg-turbo-dev` (none flagged in jp2a's README). Built fine in stage 1; runtime needs the matching `libpng/libwebp/libexif` packages.
- **Structurizr CLI version pin** — original guess `2024.12.04` was a 404; bumped to `2025.11.09` (current latest).
- **PlantUML stdlib include path** — corrected to point at the `dist/` subdirectories of the AWS / Azure / GCP icon repos (the top-level paths don't contain the `.puml` macros).
- **PlantUML output subdir trick** — PlantUML's `@startuml NAME` overrides the input filename for the output, which silently overwrites siblings. Renderer now writes each `.puml` into its own subdir (`plantuml/<name>/` and `plantuml/<name>.xkcd/`) to avoid collisions and to keep default + handwritten variants separate.
- **Image-size cleanup pass** — initial build was 722 MB; aggressive stripping of vendor `.git`, `scripts/`, `source/`, dev-tooling JARs, and non-`.puml` files inside the PlantUML stdlib repos brought it to 618 MB. Final size after JRE swap: **622 MB**.
- **Gallery generated by bash heredocs in `render-batch.sh`** — Jinja2 + a separate `generate-index.py` was the original plan, but a self-contained bash generator turned out simpler for the research phase. Easy to swap to Jinja2 later if needed.
- **Single-file mode, stdin→stdout mode, `manifest.json`, `asciidag-from-git`** — all still TODO. Deferred until the gallery output is signed off.
- **`README.md`** — not yet written; planned for after Phase 5 stabilises.

## Development phases

### Phase 1 — `SPEC.md` (lazy, brief)
Single high-level document covering the project, who it's for, accepted
inputs, produced outputs, invocation modes, out-of-scope items, and a repo
layout placeholder.

**Acceptance**: user reads it and OKs it.

### Phase 2 — `TECH_STACK.md` (skeleton)
Bare list of bundled tools, grouped by purpose. One line per tool: name,
what it renders, source (apk / jar / binary / script). Versions filled in
once Phase 3 confirms what installs cleanly.

**Acceptance**: user confirms the tool list matches expectations.

### Phase 3 — `Containerfile` + iterate until clean build
Build with `podman build`, iterate until:
- Build completes
- Every bundled tool answers `--version` or `--help` (or equivalent)
- `tests/verify-tools.sh` runs inside the container, prints one-line
  PASS/FAIL per tool, exits 0 if all PASS

**Deliverables**:
- `Containerfile`
- `tests/verify-tools.sh`
- `Makefile` with `build` and `verify` targets
- `scripts/wrappers/{plantuml,ditaa,structurizr}` shims (needed for verify)

**Acceptance**: `make verify` exits 0 with every tool reporting its version.

### Phase 4 — Demo input files
A small starter set covering each tool family. User will add more.

**Deliverables** (`examples/`):
- `deps.gv` — Graphviz dependency
- `sequence.puml` — PlantUML sequence
- `c4_container.puml` — PlantUML C4 (uses bundled stdlib)
- `architecture.d2` — d2
- `network.ditaa` — ditaa
- `flowchart.mmd` — Mermaid flowchart
- `workspace.dsl` — Structurizr DSL
- `examples/README.md` — what each example demonstrates

**Acceptance**: user reviews, adds their own examples.

### Phase 5 — Renderers, gallery, manifest, iteration
Build the actual rendering pipeline against Phase 4 inputs. Iterate
visually with the user.

Sub-deliverables:
- Per-tool renderer scripts (`scripts/lib/render-*.sh`)
- Batch entry point (`scripts/render-batch.sh`) — scans `/input`,
  dispatches by extension, writes to `/output/<tool>/`
- `scripts/generate-manifest.py` → `/output/manifest.json`
- `scripts/generate-index.py` → `/output/index.html` (one section per tool,
  source code shown next to rendered output)
- Mermaid + helpers loaded via CDN in the gallery (no server-side Mermaid)
- Single-file mode: `swgraph render path/to/file.ext`
- Stdin→stdout mode: `cat file | swgraph render --format X --to svg`
- Optional `--xkcd` flag: PlantUML `handwritten true`, d2 `--sketch`
- Optional `serve` subcommand: `python3 -m http.server` against `/output`
- `swgraph asciidag-from-git --repo <path>` — brownfield analysis helper

**Acceptance**: `make render` produces a gallery the user is happy with;
iterate per-tool until each rendering looks right.

## Containerfile strategy (Phase 3)

Multi-stage Alpine 3.21 build.

**Stage 1 — `downloader`** (alpine:3.21 + curl, tar, unzip, git, build-base, libjpeg-turbo-dev)
- Fetch plantuml-1.2026.3.jar
- Fetch ditaa-0.11.0-standalone.jar
- Fetch + extract d2-v0.7.1-linux-amd64.tar.gz
- Fetch + extract Structurizr CLI zip
- `git clone --depth=1` C4-PlantUML, AWS-icons, Azure-icons, GCP-icons,
  puml-themes (strip `.git`, `*.md`, `images/` to shrink)
- Fetch xkcd-script.ttf and xkcd.otf
- `git clone` jp2a + `make` → static binary

**Stage 2 — final** (alpine:3.21)
- apk: `graphviz openjdk17-jre-headless rsvg-convert imagemagick python3
  py3-pip py3-cairosvg py3-jinja2 uv chafa perl perl-app-cpanminus bash
  fontconfig font-dejavu libjpeg-turbo git tini`
- `cpanm --notest --no-man-pages Graph::Easy`, then `apk del perl-app-cpanminus`
- COPY artifacts from stage 1
- `fc-cache -fv` to pick up xkcd font
- COPY `scripts/wrappers/` and symlink each into `/usr/local/bin/`
- `ENV PLANTUML_INCLUDE_PATH=/opt/plantuml-stdlib/c4:.../aws:.../azure:.../gcp:.../themes`
- `WORKDIR /input`, `ENTRYPOINT ["/sbin/tini", "--"]`

Estimated final image: **~430 MB**.

## Risks / call-outs (to land in README during Phase 5)

- **xkcd font is CC BY-NC 3.0** — non-commercial use only.
- **PlantUML jar is current upstream (1.2026.3)**, not the 5-year-old
  VSCode-bundled 1.2021.00 the source doc references.
- **Mermaid renders client-side via CDN** — `file://` works in modern
  browsers; corporate browsers blocking CDNs need `swgraph serve`.
- **`.py` execution**: render-batch will NOT execute arbitrary Python from
  `/input`. asciidag is invoked through the dedicated helper, not via user
  Python files.
- **AWS/Azure/GCP icons vendored at build time** — refresh by rebuilding.
- **linux/amd64 only** — d2 binary download is amd64-specific. Multi-arch
  is a later enhancement.

## Phase 6 — CLI Entrypoint (`scripts/swgraph`)

**Goal**: A Python script that is the container's primary interface. Accepts
one or more diagram source files, renders them, and produces SVG + PNG
artifacts. The gallery (`render-batch.sh`) then becomes a consumer of this
script rather than owning the rendering logic itself.

### 6A — `scripts/swgraph` (the entrypoint)

**Implementation language**: Python 3 (already in the container).

**CLI interface**:

```
swgraph render [OPTIONS] FILE [FILE...]

Options:
  -o, --output DIR        Output directory (default: /output)
  --sketch                Enable hand-drawn/xkcd style
  --mermaid-backend CMD   'mmdc' (default) | 'isomorphic' (experimental)
  -q, --quiet             Suppress info messages
  -v, --verbose           Show tool stdout/stderr
  --help                  Show usage
```

**Supported formats** (dispatched by extension):

| Extension | Tool | SVG | PNG | Notes |
|-----------|------|-----|-----|-------|
| `.gv`, `.dot` | Graphviz | yes | yes | Engine auto-detected from `layout=X` in source; fallback: `dot` |
| `.puml`, `.plantuml` | PlantUML (+ C4, AWS, Azure, GCP stdlibs) | yes | yes | `--sketch` → handwritten mode + xkcd font |
| `.d2` | d2 | yes | yes | `--sketch` → d2's built-in sketch mode |
| `.ditaa` | ditaa | no | **yes** | ditaa only outputs PNG natively |
| `.mmd`, `.mermaid` | mmdc / isomorphic-mermaid | yes | yes | mmdc is default; `--mermaid-backend isomorphic` for evaluation |
| `.dsl` | Structurizr CLI → PlantUML | yes | yes | All views rendered (multi-output) |

**Output naming**:
- Input `deps.gv` → `OUTPUT/deps.svg` + `OUTPUT/deps.png`
- Structurizr `workspace.dsl` (multiple views) → `OUTPUT/workspace-ViewName.svg` + `.png`

**SVG → PNG conversion**: `rsvg-convert -f png -o OUT.png IN.svg`

**Font embedding** (`--sketch` mode): Embed xkcd-script.ttf as base64 data URI
inside each produced SVG so it is self-contained.

**Error handling**: If a file fails to render, log the error and continue.
Exit non-zero at the end if any file failed.

**Script structure** (~250–300 lines Python):

```
scripts/swgraph
├── CLI arg parsing (argparse, subcommands)
├── dispatch_file()           # extension → render function
├── render_graphviz()         # $engine -Tsvg; engine from layout= directive
├── render_plantuml()         # plantuml -tsvg
├── render_d2()               # d2 src out.svg
├── render_ditaa()            # ditaa src out.png
├── render_mermaid()          # mmdc -i src -o out.svg
├── render_structurizr()      # structurizr export → plantuml → svg (per view)
├── svg_to_png()              # rsvg-convert wrapper
├── embed_xkcd_font()         # base64 font injection into SVG
└── summary + exit code
```

### 6B — Containerfile changes (Mermaid support)

Add to the runtime stage:

1. `apk add chromium ttf-dejavu` (~130–180 MB)
2. `npm install -g @mermaid-js/mermaid-cli` with `PUPPETEER_SKIP_DOWNLOAD=true` (~60–80 MB)
3. Write `/etc/mmdc.json`: `{"executablePath":"/usr/bin/chromium-browser","args":["--no-sandbox"]}`
4. Install isomorphic-mermaid for evaluation: `npm install -g isomorphic-mermaid resvg-js`
5. COPY `scripts/swgraph` → `/opt/swgraph/swgraph`, symlink `/usr/local/bin/swgraph`
6. Update CMD: `CMD ["swgraph", "--help"]`

**Estimated image size**: ~850–900 MB (up from 622 MB; chromium is the bulk).

### 6C — Rework `render-batch.sh` to use `swgraph render`

The gallery script becomes an **orchestrator**:

1. Loop over `/input/*.{gv,puml,d2,ditaa,mmd,dsl}`
2. For each file: `swgraph render -o /output/<tool>/ FILE` (default render)
3. For gallery comparison variants:
   - Graphviz: call once per engine (inject temporary `layout=X`)
   - All tools: call again with `--sketch` for xkcd variant
4. Generate `index.html` gallery (HTML generation stays here or moves to a
   Jinja2 template — separate concern from rendering)

`render.sh` (host-side) stays as a convenience launcher but invokes the
container's entrypoint directly instead of overriding it.

### 6D — Acceptance criteria

- `swgraph render examples/deps.gv` → produces `deps.svg` + `deps.png` in `/output`
- `swgraph render --sketch examples/deps.gv` → xkcd-style SVG with embedded font + PNG
- `swgraph render examples/*.puml examples/*.d2 examples/*.mmd` → all rendered, failures logged
- `swgraph render examples/workspace.dsl` → one SVG+PNG per view
- `swgraph render examples/network.ditaa` → PNG only, no error
- Exit code 0 if all succeeded, non-zero if any failed
- `make render` (gallery) still works end-to-end using the new entrypoint
